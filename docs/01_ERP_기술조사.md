# ERP 기술 조사

> 목적: 상용 ERP 개발에 앞서 시장의 주요 ERP가 **어떤 기술과 구조**로 만들어졌는지 정리하고, 우리 제품에 가져올 설계 교훈을 뽑는다.
> 범위: 글로벌 상용 ERP, 오픈소스 ERP, 국내 ERP, 공통 기술 요소, 한국 시장 필수 연동.
> 주의: 제품 버전·가격·라이선스 조건은 수시로 바뀌므로 도입·인용 전에 공식 자료로 재확인한다.

## 2. 제품별 핵심 기술과 교훈

### 2.1 SAP S/4HANA
- **Universal Journal (테이블 `ACDOCA`)**: 과거 FI(재무)·CO(관리회계)·자산·자재원장이 각각 테이블을 가졌던 것을 **하나의 라인아이템 테이블**로 통합. 합계 테이블을 없애고 조회 시 집계(인메모리 DB 덕분).
- **Clean Core**: 표준 코드를 고치지 않고 API(OData)·이벤트로만 확장 → 업그레이드 비용 최소화.
- **Fiori**: 역할(Role) 기반 앱 단위 UX.
- **교훈**: ① 모든 거래가 최종적으로 **하나의 원장 라인 테이블**로 모이게 한다. ② 고객 커스터마이징은 **코어 수정이 아닌 확장 포인트**로.

### 2.2 Oracle NetSuite
- 처음부터 **멀티테넌트 SaaS**로 설계. 고객별 커스터마이징은 SuiteScript(JS)·커스텀 필드·워크플로로 처리.
- 다중 법인(OneWorld), 다중 통화, 연결회계를 기본 제공.
- **교훈**: SaaS 상용화 시 "고객별 포크" 없이 **설정·스크립트·커스텀 필드**로 차이를 흡수해야 운영이 가능하다.

### 2.3 Microsoft Dynamics 365 Business Central
- 원본 소스 직접 수정(구 NAV 방식)을 버리고 **Extension 모델**로 전환 → 버전업이 쉬워짐.
- Power Platform(BI·자동화)·Office·Teams와 연동이 강점.
- **교훈**: 업그레이드 가능한 확장 구조가 상용 ERP의 유지보수 비용을 결정한다.

### 2.4 Odoo
- "모든 것은 모듈": 판매·구매·재고·회계·MRP·인사가 독립 모듈, 의존성 선언으로 설치.
- **ORM 중심**: 모델(`models.Model`) 정의 → 테이블·폼·리스트 뷰·권한이 자동 연결. `_inherit`로 기존 모델에 필드/로직 추가.
- 뷰는 XML(QWeb), 프런트는 자체 OWL 프레임워크. 외부 API는 XML-RPC/JSON-RPC.
- 레코드 규칙(Record Rule)으로 행 단위 권한, 멀티 컴퍼니 지원.
- 회계는 `account.move`(전표) / `account.move.line`(분개 라인) 2 테이블이 핵심 → 판매·구매·재고가 모두 전표를 생성.
- **교훈**: ① 모듈 경계 + 상속형 확장. ② 판매/구매/재고 → **자동 분개** 구조. ③ 오픈 코어(Community/Enterprise) 비즈니스 모델.

### 2.5 ERPNext (Frappe Framework)
- **DocType = 메타데이터**: 필드·폼·리스트·권한·워크플로를 JSON 메타데이터로 정의하면 테이블·REST API·UI가 자동 생성. 고객은 UI에서 커스텀 필드/폼 추가.
- 문서 생명주기: Draft → Submitted → Cancelled (제출 후 수정 불가, 취소·수정본(Amend)으로만 변경).
- 백그라운드 작업: Redis + RQ 워커, 실시간 알림: Socket.io, 출력물: Jinja 템플릿 → PDF.
- **교훈**: ① **확정 문서 불변 + 취소/정정** 방식. ② 메타데이터 기반 커스텀 필드. ③ 인쇄 양식을 템플릿으로 고객이 수정.

### 2.6 iDempiere / OFBiz / Dolibarr
- iDempiere: **Application Dictionary**(테이블·윈도우·탭·필드를 DB에 정의) + OSGi 플러그인. 메타데이터 ERP의 원조(Compiere 계열).
- OFBiz: 엔티티·서비스를 XML로 선언하는 프레임워크. 데이터 모델 레퍼런스("The Data Model Resource Book" 기반)로 참고 가치가 큼.
- Dolibarr: 단순한 PHP 모듈 구조, 소상공인용. 기능 범위 최소 기준선으로 참고.

### 2.7 국내 ERP (더존·영림원·이카운트)
- 공통 강점: **한국 세무·회계 실무**(전자세금계산서, 부가세 신고서, 원천세, 4대보험, 연말정산), 세무사·회계사 생태계, 은행·카드 연동.
- 더존: 중소 회계 시장 점유율이 높고 세무사 사무소와 연결된 생태계. 중견용 Amaranth 10, 클라우드 WEHAGO.
- 영림원: 중견 제조업 중심, 커스터마이징형 구축.
- 이카운트: 저가 SaaS, 설정 기반, 빠른 도입.
- **교훈**: 한국 시장에서는 **세무 신고까지 이어지는 회계·급여 정확성**과 **엑셀 수준의 그리드 UX**가 구매 결정 요인이다.

## 3. ERP 공통 기술 요소

### 3.1 아키텍처 패턴
| 패턴 | 설명 | 채택 사례 | 평가 |
|---|---|---|---|
| 모듈러 모놀리스 | 하나의 배포 단위, 내부는 모듈 경계 엄격 | Odoo, ERPNext, Business Central | ERP 트랜잭션(전표·재고 동시 갱신)에 유리. **초기 권장** |
| 마이크로서비스 | 도메인별 서비스 분리 | 대형 SaaS 일부 | 분산 트랜잭션·운영 비용 큼. 소규모 팀엔 과함 |
| 메타데이터 기반 | 화면·필드를 데이터로 정의 | ERPNext, iDempiere | 커스터마이징에 강함. 전면 도입은 프레임워크 개발 비용 큼 → **커스텀 필드 수준만 부분 도입** |
| 확장(Extension) 모델 | 코어 수정 금지, 훅/이벤트로 확장 | SAP, BC | 상용 제품 업그레이드에 필수 |

### 3.2 멀티테넌시 (SaaS 상용화 시)
| 방식 | 격리 | 운영 비용 | 비고 |
|---|---|---|---|
| 테넌트별 DB | 최고 | 높음 | 대형/온프레미스 고객, 규제 고객 |
| 테넌트별 스키마 | 중간 | 중간 | 마이그레이션이 테넌트 수만큼 |
| 공유 테이블 + `tenant_id` + PostgreSQL RLS | DB 정책으로 보장 | 낮음 | 중소 SaaS 표준. 대형 고객은 전용 DB로 분리 가능하게 설계 |

### 3.3 회계 엔진
- **복식부기**: 모든 전표는 차변 합계 = 대변 합계. DB 제약 또는 트랜잭션 내 검증 필수.
- **보조원장 → 총계정원장 자동 분개**: 매출·매입·입출고·급여가 "분개 규칙(Posting Rule)"에 따라 전표를 생성.
- **확정 후 불변**: 확정 전표는 수정 불가, 역분개(Reversal)로 정정. 회계 기간 마감(Period Close) 후 해당 기간 거래 차단.
- **금액 타입**: 부동소수점 금지, `NUMERIC(18,2)` 등 고정소수. 원화 절사/반올림 규칙 명시.
- 다중 통화(거래통화/기능통화, 환율 테이블, 외화평가), 다중 회사·사업장(부가세는 사업장 단위 신고).

### 3.4 재고·원가
- 재고 수불부(Stock Ledger): 입출고 이벤트를 append-only로 기록하고 잔량은 집계/스냅샷.
- 평가 방식: 이동평균(국내 중소 제조업 일반적), 선입선출, 표준원가.
- 동시성: 같은 품목·창고 출고 경쟁 → 행 잠금(`SELECT ... FOR UPDATE`) 또는 낙관적 잠금.
- 제조: BOM, 라우팅, MRP(소요량 계산), 작업지시 — MES와 경계 정의 필요.

### 3.5 공통 기반 기능
- 문서 번호 채번(테넌트·문서유형·연도별, 결번 정책), 문서 상태 머신, 승인 워크플로(전자결재 연동).
- RBAC + 데이터 범위 권한(회사·사업장·부서), 감사 로그(누가·언제·무엇을 전/후 값).
- 배치/스케줄 작업(마감, MRP, 일괄 발행), 이벤트 아웃박스(외부 연동 신뢰성), 멱등키.
- 출력물(세금계산서·거래명세서·견적서 PDF), 엑셀 업/다운로드, 대량 데이터 그리드.

### 3.6 프런트엔드: 그리드가 핵심
| 그리드 | 라이선스 | 비고 |
|---|---|---|
| AG Grid | Community MIT / Enterprise 상용 | 사실상 표준. 엑셀식 편집·그룹핑은 Enterprise 기능 다수 |
| TanStack Table | MIT | 헤드리스, UI 직접 구현 필요 |
| Handsontable | 상용(비상업 무료) | 엑셀 유사 UX |
| RealGrid, IBSheet, Wijmo | 상용 (국내 SI에서 많이 사용) | 국내 ERP 화면 관행에 익숙 |

출력물: HTML 템플릿 → 헤드리스 브라우저(Playwright/Puppeteer) PDF가 가장 단순. 국내 리포팅 툴(OZ Report, ClipReport 등)은 비용 대비 필요 시만.

## 4. 한국 시장 필수 연동·규제

| 항목 | 내용 | 구현 방법 |
|---|---|---|
| 전자세금계산서 | 법인 및 일정 규모 이상 개인사업자 의무. 발급 후 국세청 전송 기한 존재(발급일 다음날까지) | 국세청 직접 연계는 시스템사업자 등록·인증 부담 → **연계 API 사업자(팝빌, 바로빌, 스마트빌 등)** 사용이 일반적 |
| 매입 세금계산서·카드·현금영수증 수집 | 홈택스 데이터를 매입 전표로 | 연계 사업자 API 또는 데이터 수집 API(CODEF, 쿠콘 등) |
| 부가가치세 신고 | 매출·매입처별 합계표, 신고서 서식 | 사업장 단위 집계 + 홈택스 전자신고 파일 생성 |
| 사업자 상태 조회 | 거래처 휴·폐업 확인 | 국세청 사업자등록 상태조회 API (공공데이터포털) |
| 은행 연동 | 계좌 거래내역 조회, 이체 | 오픈뱅킹(금융결제원), 펌뱅킹(은행 계약), 데이터 수집 API |
| 급여·4대보험·원천세·연말정산 | 요율·간이세액표가 **매년 변경** | 요율/세액표를 코드가 아닌 **연도별 기준 데이터**로 관리 |
| 개인정보보호법 | 주민등록번호 등 고유식별정보 **암호화 저장 의무**, 접근기록 보관 | 컬럼 단위 암호화(AES-256-GCM), 키 분리, 조회 로그 |
| 장부 보관 | 국세기본법상 장부·증빙 5년 보관 | 삭제 대신 보관 정책, 백업 |
| 회계 기준 | K-IFRS(상장사 등), 일반기업회계기준(비상장 중소) | 계정과목 템플릿을 기준별로 제공 |
| SaaS 보안 인증 | 고객사 요구 시 ISMS-P, 공공 납품 시 CSAP | 설계 단계부터 접근통제·로그·암호화 반영 |
| 주소 | 도로명주소 | 행정안전부 도로명주소 API |

## 5. 우리 제품에 가져올 설계 교훈 (요약)

1. **단일 원장**: 모든 모듈 거래 → 분개 규칙 → 하나의 분개 라인 테이블 (SAP ACDOCA, Odoo account.move.line).
2. **확정 문서 불변 + 취소/정정** (ERPNext Submit/Cancel/Amend, 회계 역분개).
3. **모듈러 모놀리스**로 시작, 모듈 간 호출은 공개 서비스 인터페이스/도메인 이벤트로만.
4. **코어 수정 없는 커스터마이징**: 커스텀 필드(JSONB), 인쇄 양식 템플릿, 승인 규칙 설정, 웹훅 (NetSuite·BC·SAP Clean Core).
5. **멀티테넌트 우선 설계**(tenant_id + RLS), 단 같은 코드로 단일 테넌트 온프레미스 설치 가능하게.
6. **한국 세무를 1급 기능으로**: 전자세금계산서·부가세·급여 기준 데이터를 초기부터.
7. **엑셀 수준 그리드 UX**와 엑셀 업로드(기존 ERP 데이터 이관)는 영업상 필수.
8. **GPL 오픈소스 ERP 포크 주의**: ERPNext(GPLv3)·iDempiere(GPLv2) 기반 제품을 배포(온프레미스 납품)하면 소스 공개 의무가 생긴다. 자체 개발 또는 LGPL/Apache 계열만 참고·활용.

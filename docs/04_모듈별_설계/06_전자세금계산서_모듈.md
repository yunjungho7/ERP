# 06. 전자세금계산서 모듈 설계 계획서

> 목적: 매출·매입의 세무 확정 계층 — 발행(정/수정)·국세청 전송 상태 추적·매입 수집. 연계 사업자 API 뒤에 어댑터를 두어 사업자 교체 가능 구조.
> 우선순위: P0 (국내 필수). 공통 프레임워크는 [00_공통_설계기반.md](00_공통_설계기반.md) 참조.

---

## 1. 범위

- 포함: 정(세금)계산서 발행·일괄발행, 수정계산서, 국세청 전송 상태 추적, 매입 수집→매칭, 발행 이력, 홈택스 자료 비교
- 제외: 계산서·영수증 수집(P1), 카드·현금영수증 스마트 증빙(P1), 원천세(P2)

## 2. 화면/메뉴

| 메뉴 | 기능 |
|---|---|
| 발행 대기 | 매출 posted분 중 미발행 — 선택 일괄 발행 |
| 발행 진행단계 | 접수→발행→국세청 전송→완료 상태 추적, 실패 재시도 |
| 수정 세금계산서 | 수정사유 선택 + 원본 참조 수정본 발행 |
| 매입 수집 | 홈택스 수집분 목록 → 매입전표 매칭/초안 생성 |
| 발행 이력 | 기간·상태·거래처별 조회, 재전송·인쇄 |
| 홈택스 자료 비교 | 우리 발행 내역 vs 국세청 등록 내역 불일치 조회 |
| 증빙 수집 | 카드매입·현금영수증·계산서 수집 (P1) |
| 연계 설정 | 사업자 선택·인증 정보·동기화 스케줄 |

## 3. 데이터 모델

| 테이블 | 주요 컬럼 |
|---|---|
| `tax_invoice` | id, nts_confirm_no(국세청 승인번호), type(정/수정), issue_type(정발행/역발행/위수탁), supplier_site_id, recipient_partner_id, 양자 스냅샷(사업자번호·상호·대표·주소·업태종목·담당자메일), supply_amt, tax_amt, item_desc, write_date, status(draft→issued→sent→confirmed / failed / cancelled), mgt_key, modify_reason_code, original_id, api_provider, api_tx_id |
| `tax_invoice_line` | 일자, 품목명, 규격, 수량, 단가, 공급가액, 세액, 비고 |
| `tax_invoice_purchase` | 매입 수집분 — nts_confirm_no, 공급자 스냅샷, 일자, 금액, matched_purchase_invoice_id, status(collected→matched→confirmed/unmatched) |
| `tax_api_log` | provider, request/response, mgt_key, retried, error |
| `tax_policy` | 테넌트 설정: 자동발행 여부, 발행 대기 기본, 연계 사업자, 인증서 |

## 4. 상태머신

```
draft ──issue──▶ issued ──send──▶ sent ──confirm──▶ confirmed
  │                │               │                      │
  └──cancel────────┴─── 실패는 failed (재시도 가능)        │
                 ▲                                        │
   수정: original_id 참조의 수정계산서 (사유 코드 필수)      │
```

- `sent` 이후 국세청 상태는 비동기 — 폴링 또는 사업자 콜백으로 갱신.
- 발행 기한: 발급일 **다음날까지 전송** 의무 → 기한 경과 목록에 경고 배지.

## 5. 어댑터 인터페이스 (사업자 교체 가능)

```ts
interface ITaxBillProvider {
  issue(draft: TaxInvoice): Promise<{mgtKey, txId}>         // 발행+국세청 전송 요청
  cancel(mgtKey, reason): Promise<void>                     // 발행취소
  modify(originalMgtKey, modified: TaxInvoice, reason): ...  // 수정계산서
  getStatus(mgtKey): Promise<TaxInvoiceStatus>              // 전송 상태
  collectPurchases(from, to): Promise<PurchaseData[]>        // 매입 수집
}
```

- 구현: Popbill / Barobill / SmartBill 중 1사 선정(02 §10-5) + Mock 어댑터(테스트).
- 인증서·인증정보는 사업자 측 보관 방식, 우리 측에는 API 키만 저장(비밀번호 관리자).
- 호출은 전부 `tax_api_log` 기록 + 실패 재시도(지수 백오프) + 멱등키로 중복 발행 방지.

## 6. API 스케치

```
/tax/invoices              GET/POST (발행 대기 조회 포함)
POST /tax/invoices/{id}:issue :cancel :resend        # 발행·취소·재전송
GET  /tax/invoices/{id}/status                       # 전송 상태 즉시 조회(사업자 경유)
/tax/invoices/{id}/modifications  POST               # 수정계산서
/tax/purchases             GET, POST /{id}:match {purchase_invoice_id}
/tax/provider-logs         GET (tax_api_log 조회)
/tax/policies              GET/PATCH (연계 설정)
```

## 7. 연동·이벤트

- 구독: `sales_invoice.posted` → 발행 초안 생성(설정: 대기 목록 또는 즉시), `sales_return.posted` → 수정계산서 후보
- 발행: `tax_invoice.state_changed` → 영업 매출 화면 배지·알림, `tax_invoice_purchase.collected` → 구매 모듈 매칭 대상 추가
- 매입 수집: 스케줄(일 1회+) → `tax_invoice_purchase` → 구매 모듈 매칭

## 8. 비즈니스 규칙·검증

- 공급가·세액 반올림 = 라인별 반올림 후 합계(매출과 동일 규칙).
- **공급시기 판정**: 재화 인도일·용역 제공완료일을 `supply_date`로 하며, 작성일자(`write_date`)와 다를 경우 경고. 월합산 등 공급시기 특례는 테넌트 설정으로 허용.
- 발행 전 검증: 공급받는자 사업자 상태조회(휴·폐업 경고), 필수 스냅샷 완비.
- 수정계산서 사유 코드(공급가 변동·기재사항 착오·계약 해제 등) 필수, 원본 참조 필수.
- 동일 매출의 중복 발행 차단: `sales_invoice ↔ tax_invoice` 1:활성1 (수정분 별도 체인).

## 9. 수용 기준

- [ ] 매출 확정 → 발행 대기 → 발행 → 전송 상태 추적 종단
- [ ] 수정계산서가 원본·사유로 추적 가능
- [ ] 매입 수집분이 매입전표와 자동 매칭, 불일치 수기 처리
- [ ] Mock 어댑터로 전 흐름 테스트, 사업자 교체 시 코어 코드 무수정
- [ ] 발행 기한 경과 건 경고 표시

## 10. 후순위·미결

- 스마트 증빙(카드·현금영수증→자동 전표 초안), 위수탁·역발행 자동화, 현금영수증 발행 — P1~P2
- 미결(02 §10-5): 연계 사업자 선정 — 과금·기능·안정성 비교 후 1사, 어댑터로 격리
